- **R0** — `/charly-distros:container-nesting` (this repo's own skill) and `/charly-build:validate` were read before the edit; the candy and the skill body move together, per this repo's `AGENTS.md`.
- **R1** — two failures surfaced in this gate; both were RCA'd before any remediation, and both are filed (see `## Filed issues`).
  1. **The first bed run failed at the FIRST BASE RESOLVE of the image chain**, not in the changed candy: `failed to resolve source metadata for ghcr.io/opencharly/arch:2026.302.0815: not found`. *Mechanism*: a local multi-stage build bridges each built stage into the local charly OCI registry (`CHARLY_BUILD_REGISTRY_MIRROR`) so the next stage's `FROM` resolves locally; with the knob unset the drive pushes nothing, the resolve went upstream to `ghcr.io`, and the private `opencharly/arch` package denied it. *Missed control*: the drive has no preflight that names the mirror when a chain's base resolves upstream, so the error points at GHCR rather than at the missing knob — the same handshake skew as `opencharly/plugin-build#35`, in the opposite direction (there the DAEMON lacked the mirror; here the DRIVE did). *Blast radius*: every local multi-stage build in a shell without the knob, not this change. *Root fix applied*: the knob is exported for the gate run, and the evidence is on `opencharly/plugin-build#35`.
  2. **A standalone `charly box build crabbox-e2e` (a redundant step of the gate script, not the bed) was SIGKILLed** with `signal: killed` after 7 m 41 s, while the buildkitd daemon's own log shows the solve still running (`Solve returned error: rpc error: code = Canceled desc = context canceled`, with per-exec probes up to 10 s before the cancel). *Mechanism*: `charly box build` is a plugin→plugin call, and that leg arms charly's **idle no-progress bound** (`charly/plugin_dispatch_reverse.go:159` → `idleBoundedContext`, class `ClassBuild` → the 90 s spec fallback). Its progress sources are host reverse legs and the peer plugin's live process-tree CPU — and the CPU source is **dead for a compiled-in peer** (`providerPid` → 0 for anything but a `*grpcProvider`, and `plugin-build` is compiled in), while the build's real work lives in the separate buildkitd daemon's tree. The bound cancelled the context; the SDK's `exec.CommandContext` SIGKILLed the `buildctl` child; and because the build reports its failure as a **reply payload** (`spec.BuildReply.Error`), the cancel cause — which carries the bound and the stall report — never reached the operator. *Missed control*: the CPU source assumed the peer is a separate process (#699's tree walk), and the reply-payload path drops the cause (#1003's complaint, recurring on a leg its fix did not cover). *Blast radius*: every long cold build on that path; each such failure is reported as an unqualified `signal: killed`. *Root fix*: charly core — a live progress source for a compiled-in peer, and the bound named on the reply-payload path. Filed as `opencharly/charly#1088`. The bed's own build of the same image was warm and green, so this is non-blocking for this change.
